# S4 parity gate — candidate-population parity (issue #102)

**Stage:** COMPUTE_CORE_SPEC §8 S4 · **Date:** 2026-08-12
**Gate:** the `evaluate` loop's candidate population matches the Python lab on
the fixture set — per-bar evaluations bit-identical, the D-026 episode-key
population identical, and the loop's summary reconciling with the lab.
**Oracle tree hash (frozen):** `2854f8c30fe59a25ef617d0357cd2fc71faa9b0b`
(`git rev-parse HEAD:src/v8`) — any change to `src/v8` invalidates this result.

## What was compared

Both implementations run over the SAME synthetic fixture
(`make_synthetic_tape(seed=7, n_bars=120, continuous=True)`, SOLUSDT) with all
28 registered experts:

- **Python oracle:** `v8.lab.Lab.run` (PHASE 3 canonical expert_id order),
  emitting `evaluations.jsonl` + `candidates.jsonl`.
- **Compute plane:** `v8-core evaluate <request.json>` (`runloop.rs` —
  `{tape_path, universe, history_depth, experts: [], max_heat, max_cluster_heat,
  base_interval, manifest}`; empty `experts` = the full 28-expert dispatch
  table), emitting the same two ledgers.

Three comparisons (test file `tests/parity/test_parity_s4_population.py`):

1. **(a) per-bar evaluations bit-identical** — every `(knowledge_time,
   expert_id)` record's `applicability`, `decision` and, on CANDIDATE, the
   draft's `direction`, `birth_time`, `risk_geometry` (IEEE-754 bit compare,
   `runner.compare_value`), `setup_fingerprint`, `setup_anchor_event_id`.
2. **(b) D-026 episode-key population** — the set of DETECTED episode-key
   inputs (`expert_id | expert_version | instrument | direction |
   setup_anchor_event_id` + the structural geometry feeding `geometry_version`)
   is identical, and the `suppressed_duplicate` set is identical (same count,
   same `(birth_time, expert_id)` identity, same episode-key inputs). Every
   suppressed row is cross-checked to duplicate an ALREADY-DETECTED episode.
3. **(c) summary reconciliation** — the loop's `n_suppressed` equals the lab's
   suppressed_duplicate count, and the DETECTED population
   (`n_candidates + n_rejected`) equals the lab's `candidate_count`. Each
   side's counters are also reconciled against its own `candidates.jsonl`.

Identity strings (`candidate_id`, `geometry_version`, `event_hash`) are V8.2
bit-encoded (D-079) and excluded from the value comparison by
PARITY_AND_IDENTITY_SPEC §3 — the episode keys compare by their VALUE inputs,
never the hash text.

## D-053 projection note

The loop builds each expert's FeatMap through the D-053 projection
(`features::group_closure(requires_for(eid))` + `project_features`; `history`
is withheld unless the closure includes it — the same withholding the Python
view applies). Because every bar × expert decision is bit-identical
(3,360/3,360), the projection is exercised end-to-end over the full 28-expert
dispatch table in the real loop, not only under the `evaluate-check` batch
path.

## Why the exit-kind coverage matters (Wave 2 predicate-IR fixes)

The S4 exit-kind coverage card (#103) compiled the donchian `responsive` /
`significant_extreme` exit kinds — module-local subclasses the S2 E1 grid
could not exercise because they are not exported by the registry — and it
caught TWO genuine latent S2 predicate-IR bugs, both fixed in `predicate.rs`
(Wave 2, commit `5accfc6`):

1. **EXCLUSIVE `window_agg` off-by-one** — `n` counts the dropped newest bar,
   so the aggregate must run over `n - 1` bars (48/202 grid mismatches).
2. **EXCLUSIVE fail-open on short history** — `len(hist) < n` must return
   `None` like Python's `len(hist.value) < m + 1` (24/202).

These survived the S2 gate because E1 exercised only exported experts; the S4
exit-kind coverage is the evidence that the compiled-but-unexercised surface
is now pinned, and this population gate runs those exit kinds' families
(donchian_breakout) through the full loop on the fixture.

## Known limitations

- **Admission timing diverges by construction.** The loop admits at
  DETECTION: it runs the D-024 mask and the RiskGate on the detection bar and
  never releases exposure slots (`gate.release` is not called in the loop — no
  position lifecycle), so the PENDING/REJECTED split differs from the lab's
  trigger-time admission. On this fixture: the loop reports 2 admitted / 207
  rejected at detection (182 `EXISTING_EXPOSURE_CONFLICT` + 25
  `FUNDING_WINDOW`), while the lab reports 209 reaching PENDING with 134
  rejected at trigger (82 `EXISTING_EXPOSURE_CONFLICT`, 35
  `PORTFOLIO_HEAT_EXCEEDED`, 17 `TRADABILITY_MASK_VETO`). The DETECTED
  population and the suppression — the S4 gate's subject — are identical; the
  admission split is the loop's next milestone, not a parity target of this
  gate.
- **D-024 veto reason strings differ** between the two rejection ledgers: the
  lab writes the `TRADABILITY_MASK_VETO` constant as the transition reason and
  keeps the detail (`BAR_RANGE`/`DEGRADED`/`FUNDING_WINDOW`) in a separate
  `tradability_veto` record, while the loop writes the detail as the reason
  directly (`FUNDING_WINDOW`).
- The fixture is single-symbol synthetic (120 bars). The real-tape candidate
  population is the certification boundary and is not part of this gate.
- `n_candidates` (loop) does not equal the lab's `candidate_count` on its own;
  the gate asserts the DETECTED-population identity
  (`n_candidates + n_rejected == candidate_count`) and documents the split.

## Not claimed

No speed claim. The S4 gate is correctness — the candidate population the loop
produces (evaluations, DETECTED episodes, suppression) is identical to the
Python lab's on the fixture set, and the summary reconciliation is explicit
about the one structural divergence (admission timing).
