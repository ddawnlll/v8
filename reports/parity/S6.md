**Gate:** the verdict tables produced by the Rust `analysis` subcommand —
Phase-1 opportunity rows, Phase-2 slice/discovery + confirmation verdicts,

## What was built

- `tests/parity/test_parity_s6.py` — the S6 gate harness:
  - builds the fixture store **in-process** (synthetic tape → Lab → the same
    `run_phase0` certified cube/regret tables test_parity_s3 consumes);
  - runs the Python oracle phases 1-3 exactly as the Rust composition consumes
    them (analysis/mod.rs, issue #116): one store's joined dataset
    (`regret_phase1`), the discovery/confirmation halves split
    chronologically by `(birth_time, candidate_id)` with the earlier
    `ceil(n/2)` rows in discovery (FCR-V8RR-007 CONTRACT 6, mirroring the
    composition's `split_half`), and Phase-3 recoverability over the
    confirmed slices (`regret_phase3`);
  - constructs the Rust `analysis` request per the documented contract in
    analysis/mod.rs: `{tape_path, universe, out_dir, manifest, candidates,
    evaluations, outcomes, states, cube_reduced_path}` carrying the **same
    store projection** the Python oracle consumed (the store's ledgers + the
    `cube` subcommand's cube-reduced artifact);
  - calls the release binary's `analysis` subcommand and compares the three
    phase outputs field-by-field under PARITY_AND_IDENTITY_SPEC §3 semantics:
    V8.2-encoded identity strings (`candidate_id`, `manifest_id`,
    `action_id`, `state_id`) excluded from the value comparison; ints/strings
    exact; floats compared by IEEE-754 bit pattern (`struct.pack` equality).
  - If the committed stub is ever present again (`v8-core analysis` returning
    "not implemented"), the gate test **SKIPs** with a clear message — the
    harness structure is the deliverable, and the pipeline comparison flips to
    PASS when the composition lands.

### The gate comparison

```
$ .venv/bin/python -m pytest tests/parity/test_parity_s6.py -q
FAILED tests/parity/test_parity_s6.py::test_s6_analysis_matches_python_phases
```

The release binary (built from the working tree) runs `analysis` to completion
(rc=0) and writes `analysis.jsonl`, but the composition is **not yet
bit-identical** on the fixture population. The divergence census:

| Surface | Rows affected | Divergence |
|---|---|---|
| `phase1_join.epistemic_class` | 431 / 431 | py `MODEL_DERIVED` vs rust `MODEL_DERIVED_DESCRIPTIVE_NOT_YET_GATED` |
| `phase1_join.endpoint` | 62 / 62 COMPUTED | py `STOP`/`TARGET`/… vs rust `None` |
| `phase1_join.label_status` | 62 | py `MATURE` vs rust `None` |
| `phase1_join.horizon_bars` | 62 | py `3` vs rust `None` |
| `phase1_join.ambiguous_bars` | 62 | py `0` vs rust `None` |
| `phase1_join.cost_r` | 62 | py `0.07` vs rust `None` |
| `phase1_join.funding_r` | 62 | py `0.0` vs rust `None` |
| `phase1_join.mae_r` / `mfe_r` | 62 | py float vs rust `None` |
| `phase2_slice.effective_independent_episodes` | 6 slices | py `1.50` vs rust `2.00` (downstream of `horizon_bars=None`) |
| `phase2_slice.materiality_note` | 6 slices | embeds the differing `eff_n` |
| `phase2_confirmation` | 0 | empty on both sides (no CANDIDATE_SYSTEMATIC) |
| `phase3_recoverability` | 0 | empty on both sides |

Root causes (working-tree composition, issue #116):

1. **`epistemic_class` label.** The Python oracle's `join_dataset`
   (regret_phase1.py:103) emits the joined row's `epistemic_class` as the
   literal `MODEL_DERIVED`; the Rust `join_dataset` (phase1.rs:158) emits the
   module `LABEL` constant `MODEL_DERIVED_DESCRIPTIVE_NOT_YET_GATED`. The
   value field must match the oracle bit-for-bit.
2. **Cube-accumulator fields read `None`.** The Rust composition re-derives
   the ACTUAL action's cube accumulators via `replay_actual_accumulators`, which
   requires a **BOUND** snapshot. On this store the Rust `reconcile` step
   binds **0 of 431** snapshots (`n_unbound=431`, `n_executed=0`): the
   composition re-derives `episode_key` with the V8.2 Canon identity encoding
   (hash.rs, D-079), which does not reproduce the V8.0 `sha1_hex(json)`
   `candidate_id` a Python-written store carries (the Python oracle's own
   re-derivation matches the stored id — verified). The composition therefore
   cannot yet join a Python-written store's ledgers. Python phase1 reads these
   fields from the certified `cube.jsonl` ACTUAL-action row instead, so the
   two sides disagree on every COMPUTED candidate's `endpoint`/`label_status`/
   `horizon_bars`/`cost_r`/`funding_r`/`mae_r`/`mfe_r`/`ambiguous_bars`.

The Phase-2 slice verdict surface **mostly agrees**: all 72 slice keys, the
verdict distribution, `n_total_in_slice`, `n_computed`, `alpha_slate` and the
`discovery_verdict` strings match. The only slice-level divergence is
`effective_independent_episodes` (and the `materiality_note` that embeds it)
on the 6 non-empty slices — a downstream consequence of `horizon_bars=None`
in the Phase-1 join rows. So the closing work for #116 is the Phase-1
join-row fields plus their downstream slice effect.

## Known limitations

- The fixture is single-symbol synthetic (200 bars). The real-tape analysis
  is the certification boundary (FULL tier) and is not part of this gate.
- On this fixture the discovery family yields no `CANDIDATE_SYSTEMATIC`
  slice, so the confirmation and Phase-3 surfaces are empty on **both** sides;
  the fixture proves those stages agree (both empty), while their non-empty
  semantics are pinned by the per-stage Rust unit tests and by the Phase-2/3
  oracle constants they capture.
- The comparison excludes V8.2-encoded identity strings per §3 — the gate is
  a value-level bit-equality test, not an identity-equality test.

## Not claimed

No economic claim; no speed claim. The S6 gate is correctness: the analysis
composition's verdict tables must be bit-identical to the Python phases on
the same population. That is not yet true in the working tree; the harness
proves the structure and enumerates exactly what must close.
