V8.6: Production Recalibration of a Behavior-Driven Trading Research System

Research monograph, architecture specification, migration doctrine, and falsification protocol.

Primary objective: reduce V8 to the smallest scientifically defensible trading-intelligence layer and place generic execution/accounting responsibility on a production-grade trading substrate. The project is optimized for time-to-trustworthy-economic-result rather than infrastructure ownership, architectural novelty, or legacy parity preservation.

Revision: Draft V8.6-RC0 · Date: 2026-09-07 · Language: English · Primary implementation language: Rust · Proposed execution substrate: NautilusTrader · Status: PROVISIONAL / PRE-VALIDATION

Abstract

V8 began as a behavior-driven trading research program built around explicit Experts, causal market state, candidate lifecycle semantics, deterministic replay, research authority, and falsification-oriented evaluation. Over rapid AI-assisted development, the implementation accumulated parallel decision universes, simulator-specific semantics, duplicated statistical routines, dead governance subsystems, multiple reporting surfaces, and a custom USDⓈ-M execution/accounting engine carrying large semantic responsibility. Subsequent audits identified both architectural sediment and execution-validity defects. The resulting problem is not merely code size: V8 owns too many responsibilities whose correctness must be continuously re-proven before any economic result can be trusted.

V8.6 changes the objective function. The system no longer optimizes for preservation of the V8 simulator ontology or global bit-for-bit parity with a frozen Python oracle. Instead it optimizes for time to a stable, reproducible, after-cost economic verdict on a production-grade execution substrate. The behavioral research thesis remains: point-in-time market state is evaluated by explicit Expert logic that produces candidates, which are admitted under finite-capital and portfolio-risk policy. Generic order lifecycle, fills, positions, fees, funding bookkeeping, and account mutation are delegated to NautilusTrader. V8 retains causal eligibility, Expert/candidate semantics, portfolio policy, Binance-specific conformance checks not guaranteed by the substrate, independent reconciliation, and scientific promotion rules.

The same recalibration is applied to the rest of the repository. S4 becomes the single canonical decision stack; the parallel V83/opportunity decision universe is removed from the active path. Dead Kaizen governance, unused evaluation surfaces, duplicate estimators, redundant HTML reporters, dead harnesses, and generic infrastructure are archived or delegated. Persistent agent-memory architecture is rejected in favor of a minimal PI-based coding workflow where repository state and versioned specifications are authoritative.

The proposed architecture is intentionally boring: PIT data → state/features → Experts → candidate/decision/admission → OrderIntent → Nautilus → execution/cashflow ledger → reconciliation → statistics → economic receipt. V8.6 succeeds only if this path is deterministic, causally valid, venue-honest, auditable with small independent witnesses, and capable of producing a falsifiable after-cost OOS result without reconstructing a second exchange simulator or governance bureaucracy around the substrate.

1. Problem definition

1.1 The project-level failure mode

The primary failure mode is not insufficient implementation capacity. AI-assisted coding made implementation cheap enough that solved infrastructure, speculative governance, and unvalidated product semantics could be added faster than they could be reviewed, validated, maintained, or removed. This created an asymmetry:

Implementation capacity ≫ validation capacity + review bandwidth + maintenance capacity.

As a result, code existence began to substitute for demonstrated necessity. An architectural idea could rapidly become a module, a module could rapidly become a subsystem, and a subsystem could acquire tests and documentation before the project had established that the subsystem belonged in the product at all.

1.2 The economic problem

The product does not need a sophisticated research platform for its own sake. The product needs a stable process for answering a narrower question:

Does the V8 Expert system produce reproducible positive after-cost expectancy on genuinely out-of-sample data under executable market assumptions?

Any infrastructure that does not shorten the path to a credible answer is a cost center. Any simulator or evaluator that produces precise but invalid outcomes is worse than an explicit unknown.

1.3 The implementation problem

Two competing instincts emerged:

  1. preserve the custom simulator because it encodes V8-specific semantics and parity controls; or
  2. replace commodity execution/accounting with a mature trading engine and recalibrate V8 around that substrate.

V8.6 chooses the second path, while preserving the small set of V8 semantics that define the research question rather than the legacy implementation.

2. Evidence base and repository diagnosis

2.1 Static ownership audit

PROJECT_EVIDENCE The infrastructure ownership audit inspected v8-core/src as approximately 81,324 Rust lines and classified most of the tree as V8-specific product semantics rather than commodity infrastructure. Approximate ownership composition was reported as ~88% product semantics, ~7% replaceable commodity carrier, ~3% integration/adaptation, ~0.5% legacy/accidental duplication, and ~0.7% unclassified.

This finding changed the diagnosis. V8 cannot be substantially simplified merely by replacing libraries. The larger problem is semantic proliferation: too many V8-specific concepts, governance surfaces, and parallel product paths accumulated without proving that they were necessary.

2.2 Direct commodity-replacement opportunity

PROJECT_EVIDENCE The audit estimated a defensible immediate reduction of roughly 2,200–3,800 owned LOC after deleting dead/duplicate code, replacing reporting/thread-pool/CLI/RNG utilities, and accounting for new adapters. This is useful but only ~3–5% of the Rust core.

2.3 Product-semantic tribunal

PROJECT_EVIDENCE A follow-up semantic audit found materially larger simplification opportunities:

2.4 Execution-validity failure cluster

PROJECT_EVIDENCE Prior research-validity work identified a cluster of defects around the custom USDⓈ-M simulation path, including trailing-stop fill behavior, liquidation price source, funding timing, portfolio admission, leverage/margin arithmetic, same-bar stop/target handling, and risks of double-settlement after naive fixes. The exact historical scope of each defect must remain revision-bound, but the cluster demonstrates a deeper point: custom ownership of exchange execution semantics creates a large verification surface.

2.5 What the audits did not prove

The audits were predominantly static. They did not prove that NautilusTrader will reproduce correct Binance USDⓈ-M economics, that the V8 custom implementation is always wrong, that Rust compilation is the main iteration bottleneck, or that any historical PnL is valid. V8.6 therefore treats the architecture shift as a design decision with explicit acceptance gates, not as a conclusion mechanically implied by the audits.

3. Research objective, hypotheses, and success criteria

3.1 Primary research question

RQ1. Does explicit behavior-specialized Expert decomposition produce reproducible positive after-cost expectancy under a stable, causally valid execution/accounting substrate?

3.2 Secondary engineering questions

  1. RQ2. Can generic execution/accounting responsibility be transferred to NautilusTrader without reconstructing an equivalent custom engine in the adapter?
  2. RQ3. Can V8 preserve point-in-time causality, finite-capital risk policy, and venue conformance while discarding legacy simulator parity?
  3. RQ4. Can the active product path be compressed to one decision universe and one authority path without losing research-essential semantics?
  4. RQ5. Does repository simplification measurably reduce time-to-result, regression surface, and decision ambiguity?

3.3 Hypotheses

3.4 Definition of success

V8.6 is successful when one frozen Expert policy can be run end-to-end through the new path and the following are simultaneously true:

  • same frozen inputs and configuration reproduce the same candidate, intent, execution, and cashflow ledgers;
  • no decision uses data before its availability/eligibility time;
  • fees, funding, realized PnL, position state, and account state reconcile exactly once;
  • unknown venue semantics are surfaced rather than silently approximated;
  • the result is after-cost and can be labeled either NO_ECONOMIC_CLAIM or a properly supported economic verdict;
  • the active architecture contains no second default decision universe and no second sovereign simulator.

4. V8.6 doctrine: Production > Infrastructure

DESIGN_DECISION V8.6 adopts the following engineering doctrine:

  1. Infrastructure has no independent value. It exists only to shorten the path to a trustworthy product result.
  2. Solved commodity problems are dependencies by default. Custom implementations require a domain-semantic reason.
  3. V8-specific is not synonymous with necessary. Product semantics must also justify their existence.
  4. AI implementation capacity does not create organizational capacity. “The agent can code it” is not an admission criterion.
  5. Market truth outranks implementation heritage. Legacy parity is evidence, not sovereignty.
  6. Unknown is an allowed output. Missing mark prices or unobserved intrabar paths do not authorize invented certainty.
  7. One canonical path beats multiple partially governed paths.
  8. Deletion and delegation are first-class engineering work.

6. NautilusTrader as execution substrate

6.1 Why V8.6 selects Nautilus

DESIGN_DECISION The selection is not based on a claim that Nautilus perfectly implements V8's historical semantics. It is selected because the project objective now values mature order/execution/accounting infrastructure, stable production-oriented responsibility ownership, and reduction of custom exchange-state code more highly than preservation of the old simulator's ontology.

The migration therefore accepts a deliberate loss of some historical parity. Old simulator outputs become legacy evidence and failure cases rather than constitutional targets.

6.2 Known semantic gaps

The following gaps remain explicit and must not be hidden by the adapter:

  • Entry timing: bar callback timing can differ from V8's prior next-bar semantics. V8 must schedule eligibility explicitly rather than rely on engine convenience.
  • Intrabar path: engine bar heuristics are not historical path reconstruction.
  • Funding boundaries: event timing and settlement identity must be mapped explicitly and tested for exactly-once behavior.
  • Margin/account mode: generic margin models do not automatically certify historical Binance isolated-margin semantics, leverage brackets, cumulative offsets, or liquidation charges.
  • Mark-price liquidation: absence of authoritative mark data blocks authoritative liquidation claims.
  • Licensing/integration topology: process separation is the default initial topology to isolate licensing and reduce direct coupling; legal review may authorize alternatives later.

7. Disposition of the legacy USDⓈ-M simulator

7.1 Authority status

DESIGN_DECISION usdm_sim is demoted from sovereign economic authority to legacy diagnostic/reference implementation.

7.2 What is preserved

  • regression cases that encode previously discovered failures;
  • small isolated arithmetic witnesses when they are simpler than the production path;
  • historical fixtures useful for differential debugging;
  • documentation of past assumptions and failure modes.

7.3 What is not preserved

  • exact reproduction of old PnL headlines;
  • global CPython bit-for-bit parity as a release requirement;
  • legacy matching/account lifecycle simply because tests already exist;
  • simulator-specific governance or receipt machinery that duplicates the V8.6 authority path.

7.4 F1–F8 as migration assets

The validity defects discovered in the old engine are not merely reasons to discard code. They become adversarial regression cases for the new path. At minimum, V8.6 must carry targeted tests for: gap-aware trailing behavior, mark-vs-trade liquidation source, funding boundaries, risk admission, leverage/bracket arithmetic, duplicate funding prevention, purge/partition integrity where relevant, and same-bar ambiguity.

8.1 Ambiguous bars

For OHLC bars in which both stop and target could have been reached, the true path is unknown. V8.6 must not label an arbitrary engine path as historical truth. The preferred hierarchy is:

  1. use higher-fidelity trade/quote data when available;
  2. otherwise record the event as ambiguous;
  3. compute sensitivity or a bounded outcome interval where practical;
  4. block promotion if the economic conclusion depends materially on the unresolved path.

8.2 Liquidation

Liquidation claims require the correct price ontology. If historical mark-price information is absent, the system must emit an explicit status such as NO_LIQUIDATION_AUTHORITY. Trade OHLC must not be silently substituted for mark price to create false precision.

9. One canonical decision universe

9.1 S4 is canonical

DESIGN_DECISION S4 becomes the only baseline decision path for V8.6. This is not a claim that S4 is economically superior to V83. It is a complexity-control decision: one baseline is required before another decision universe can be tested.

9.2 V83 / opportunity disposition

V83/opportunity is removed from the active default path and archived as an experimental challenger. It may return only through a preregistered comparison in which it must beat S4 on an explicit metric while preserving validity and risk constraints.

Diagnostic-only surfaces around the V83 stack—write-only funnels, unused harnesses, receipt-only paths with no promotion effect—are removed unless a current consumer is demonstrated.

9.3 No hidden dual governance

No production or research command may select a second decision universe through a hidden configuration flag. A challenger is a separate experiment with an explicit manifest and must never silently share economic authority with the baseline.

10. Kaizen recalibration

10.1 Governance sediment

Static source review reported that the majority of Kaizen code was not called by the active economic path. V8.6 archives controller/verdict/validation/verification/adaptive/diagnosis/hypothesis/challenger/governance layers that exist primarily as a self-contained research bureaucracy.

10.2 What remains

Only functions with a demonstrated role in the current product path or a clearly defined offline research workflow may remain. Economic behavior-mutating overlays are disabled by default during validity restoration because they make attribution harder.

10.3 Offline iteration, not sovereignty

Kaizen may survive as an offline research assistant that proposes or records challenger hypotheses. It does not receive sovereign runtime authority and cannot silently alter a frozen policy or promote a claim.

11. Evaluation and research authority

11.1 Collapse the evidence empire

The previous architecture accumulated multiple evidence, assurance, audit, report, and authority surfaces. V8.6 replaces these with one visible sequence:

11.2 Authority rule

A module that does not feed a promotion gate or enforce a hard invariant is not “authority-critical” merely because it produces an evidence bundle. Such output may remain diagnostic, but it must be labeled and must not grow into a parallel governance subsystem.

11.3 Statistical implementation

  • One canonical implementation per statistical primitive.
  • Duplicate bootstrap/block-size/CI functions are consolidated.
  • Proxy PBO/DSR labels are forbidden.
  • If a method is not correctly implemented, the correct result is NOT_COMPUTED, not a surrogate metric with the same name.
  • External mature statistical implementations may be used as independent verification when they reduce owned responsibility.

11.4 Search and OOS lineage

Every human or agent trial counts. Opening a holdout consumes information. V8.6 maintains a minimal append-only trial ledger containing policy/config hash, dataset identity, timestamps, trial family, result status, and whether the sample remains genuinely unexposed.

13. Data contract and point-in-time causality

13.1 Causal record

Every market observation capable of affecting a decision should expose, where applicable:

event_time
effective_time
publication_time
ingest_time
availability_time
eligibility_time
source_id / source_hash
venue_sequence or equivalent ordering evidence

Not every source will have every timestamp. Missing semantics must be explicit.

13.2 Prefix invariance

LOCKED_INVARIANT Future data may not alter past decisions. If two tapes share an identical causally available prefix, all V8 decisions over that prefix must remain identical.

X≤t = X′≤t ⇒ Decision≤t(X) = Decision≤t(X′)

13.3 Execution eligibility

The fact that a bar is stamped at time t does not imply that a signal computed from that bar was executable at the same stamped price. V8.6 separates observation availability from execution eligibility and schedules intents accordingly.

14. Venue conformance layer

14.1 Scope

The venue layer is not a second simulator. It is a small set of time-versioned facts and validators required to decide whether the execution substrate is being used consistently with the intended historical venue regime.

14.2 Required historical facts

  • instrument/tick/lot/min-notional rules;
  • fee schedule and assumed account tier;
  • funding event schedule and rate source;
  • leverage brackets and cumulative offsets when margin claims depend on them;
  • account mode (isolated/cross) and position mode where material;
  • mark/index channels when liquidation or margin calculations require them.

14.3 Fail-closed policy

If a venue fact is unavailable and the result materially depends on it, the affected claim is disabled. V8.6 does not fill missing venue history with current exchange settings without an explicit assumption label.

15. Portfolio and risk authority

15.1 V8-owned risk

The following are product-level policy and therefore remain in V8:

  • finite-capital admission;
  • portfolio heat;
  • concurrency limits;
  • exposure conflict handling;
  • symbol/instrument/exposure identity mapping;
  • candidate sizing intent before venue quantization.

15.2 Engine-owned risk primitives

Nautilus may enforce generic instrument/account constraints. V8 does not duplicate them merely for symmetry. Where V8 policy is stricter than the engine, V8 rejects before producing an executable intent.

15.3 Admission token

A useful implementation pattern is to produce a small immutable admission record:

AdmissionDecision {
    candidate_id,
    decision_time,
    eligibility_time,
    quantity_intent,
    exposure_id,
    risk_budget,
    policy_version,
    accepted | rejected(reason)
}

The token is not a second order model. It records why V8 authorized an intent before the execution substrate takes over.

16. Stability definition

16.1 Mechanical stability

“Stable” in V8.6 means:

  • same frozen input + same code/config + same pinned dependency versions → same candidates;
  • same intents → same execution/cashflow ledger under deterministic backtest conditions;
  • all state transitions are reproducible and attributable;
  • no hidden state leaks across runs;
  • agent memory cannot alter economic behavior.

16.2 Economic stability

Mechanical determinism is necessary but insufficient. Economic robustness requires sensitivity analysis across plausible costs, execution uncertainty, market regimes, and genuinely out-of-sample periods. A strategy that is deterministic but collapses under small realistic perturbations is not economically stable.

17. Agent and development workflow

17.1 PI is the default harness

DESIGN_DECISION V8.6 closes the agent-platform problem. PI is the default coding harness because the current objective values a simple, transparent implementation loop more than memory-heavy orchestration.

17.2 Repository truth over persistent memory

  • Current code, tests, manifests, and versioned specifications are authoritative.
  • Persistent memory is minimized; stale architecture decisions must not silently bias new work.
  • Stable rules live in a short repository instruction file.
  • Architecture decisions live in versioned ADRs/monographs.
  • Every task begins from current repository state and explicitly named evidence.

17.3 Explicitly rejected agent work

No new agent memory graph, autonomous long-term learning layer, beads-like epistemic memory system, multi-agent governance platform, or agent benchmark infrastructure is permitted in V8.6 unless a measured development bottleneck first demonstrates need.

18. Migration program

18.1 Migration principle

The migration is not a clean-room V9 rewrite. It is a controlled recalibration of the active path. Proven product semantics are retained; legacy infrastructure authority is retired; dead semantics are archived.

18.2 Stage A — Freeze and inventory

  • pin revision, dependency versions, one reference tape, one Expert family, and current candidate schema;
  • record current output artifacts for debugging only;
  • disable feature additions.

18.3 Stage B — Semantic austerity

  • archive dead Kaizen governance;
  • archive dead evaluation surfaces and unused harnesses;
  • consolidate duplicate statistics;
  • collapse reporters into one template path;
  • mark V83/opportunity non-canonical.

18.4 Stage C — New execution boundary

Create the minimum substrate-independent contracts:

OrderIntent
ExecutionEvent
CashflowEvent
AccountSnapshot

No compatibility wrapper should preserve obsolete usdm_sim API shape unless the new path genuinely needs that shape.

18.5 Stage D — Nautilus integration

  • translate admitted V8 intents into Nautilus orders;
  • receive fills, position transitions, fee/funding events, and account snapshots;
  • reconcile all cash movements;
  • pin versions and runtime configuration.

18.6 Stage E — Venue truth

  • add historical conformance inputs;
  • enforce mark-data gate;
  • verify funding boundaries and deduplication;
  • verify minimum/lot/tick constraints and account mode assumptions.

18.7 Stage F — Authority path

  • one canonical statistical implementation;
  • one assumption/ambiguity register;
  • one trial ledger;
  • one economic receipt.

18.8 Stage G — Frozen validation run

Run the same frozen policy at least twice. Compare candidate stream, admissions, intents, fills, fees, funding, cashflow ledger, position state, and final equity. Any unexplained divergence blocks promotion.

20. Required falsification tests

20.1 Temporal tests

  • prefix invariance under appended future data;
  • availability/eligibility delay tests;
  • signal on bar N cannot receive impossible price from bar N when policy requires later eligibility.

20.2 Funding tests

  • entry immediately before funding;
  • entry exactly at funding boundary;
  • exit immediately before/at/after boundary;
  • terminal funding event;
  • replay window equivalence;
  • exactly-once settlement identity.

20.3 Execution ambiguity tests

  • gap through stop;
  • bar touches stop and target;
  • order submitted after observation cannot retroactively fill at unavailable price;
  • rejected or modified stop transition behavior.

20.4 Risk tests

  • heat=0 rejects all new admissions;
  • concurrency cap is non-bypassable;
  • exposure conflict is invariant to Expert duplication;
  • lot/min-notional boundary conditions;
  • finite capital cannot be exceeded by same-bar multiple admissions.

20.5 Accounting tests

  • cash conservation;
  • fee accounting;
  • funding accounting;
  • realized/unrealized transition consistency;
  • position close returns account to expected state.

25. Threats to validity

25.1 Production-grade does not imply correct-for-V8

Nautilus maturity cannot substitute for explicit conformance. It may contain assumptions unsuitable for the exact historical experiment, and integration can introduce new errors.

25.2 Static audit bias

Several simplification judgments originate from static call-graph/source inspection. Public APIs or unusual tooling could theoretically invoke apparently dead code. Archive-before-delete is therefore preferred for the first migration.

25.3 Semantic loss during simplification

Removing governance layers may accidentally remove a unique invariant that was poorly wired rather than truly unnecessary. Every removed subsystem should be mapped to the invariant it formerly claimed to enforce.

25.4 Data insufficiency

The current tape may be insufficient for authoritative liquidation or intrabar-path claims. Architecture cannot repair absent historical evidence.

25.5 Historical-result anchoring

Old positive backtests can psychologically anchor decisions even after simulator validity is questioned. V8.6 treats them as burned diagnostics unless re-established under the new authority path.

25.6 Rewrite temptation

Once architecture is being simplified, agents may propose adjacent redesigns. V8.6 forbids expansion during recalibration to avoid recreating the same complexity under cleaner names.

26. Reversal and rollback doctrine

A production-first decision must remain falsifiable. The system should reverse a V8.6 choice when measured evidence shows that the choice increases total verification/maintenance burden or changes the research question in an unacceptable way.

26.1 Nautilus reversal

Reconsider Nautilus if:

  • the adapter approaches the complexity of the retired engine;
  • necessary historical Binance semantics cannot be expressed without a substantial custom engine;
  • deterministic repeated runs cannot be obtained;
  • licensing constraints are incompatible with intended distribution/deployment;
  • another mature substrate demonstrably satisfies the written slice with lower total integration cost.

26.2 Semantic austerity reversal

Restore archived code only if a concrete current consumer and a unique validity/product function are demonstrated. Git history is the archive; speculative future use is not sufficient.

29. V8.6 Constitution

  1. V8 is a trading research product, not an infrastructure company.
  2. Production > Infrastructure.
  3. One decision universe, one execution boundary, one ledger, one authority path.
  4. Experts and causal research semantics are the core product; generic execution/accounting are dependencies.
  5. Legacy implementation parity is subordinate to market-valid semantics.
  6. No future data may alter a past decision.
  7. Candidate, order, fill, position, and outcome are distinct economic objects.
  8. Unknown market state is preferable to fabricated precision.
  9. No economic claim without exactly-once cashflow reconciliation.
  10. No promoted liquidation claim without the required price ontology.
  11. No adapter may recreate the dependency it claims to adopt.
  12. V8-specific code must justify itself; “custom” is not an exemption from austerity.
  13. Every added component must beat its simpler baseline or enforce a unique hard invariant.
  14. Every trial counts; OOS exposure burns information.
  15. Repository truth outranks agent memory.
  16. AI can implement a subsystem; that does not mean V8 should own it.
  17. The final architecture should look boring.

Appendix B — Definition of done

V8.6 is done when the architecture becomes boring enough that the research question is visible again.

A frozen Expert policy must pass through a single causal decision path, produce intents, execute on a pinned production-grade substrate, emit an exactly reconciled economic ledger, and produce an assumption-aware statistical receipt. The result must be reproducible without relying on hidden agent memory, a second simulator, parallel product semantics, or decorative governance layers. Only after that point may V8 resume serious alpha iteration.
